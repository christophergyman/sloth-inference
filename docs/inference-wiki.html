1. What is inference

Words you need: inference - using a trained model. training - teaching the model by changing numbers. model - the saved program that predicts. weights - the millions of learned numbers inside a model.

A model is a file full of weights, which are learned numbers. Training means finding good weights by showing many examples. Inference means freezing those weights and asking for answers.

Think of a bakery. Training is writing the recipe book. Inference is baking one cake when a customer orders.

TrainingInference
WhenOnce per model versionEvery user request, millions of times per day
WeightsChange every stepFrozen, read only [3][4]
GoalLearn wellAnswer fast and cheap
Hardware stressBig math, long runFast memory moves, many small runs

Example: you train once for weeks. Then you serve 10 million chats. Inference cost quickly passes training cost. That is why companies obsess over TTFT, cache hit rate, and tokens per second [17].

Walkthrough of one inference request: text in, tokens in, one forward pass per step, probabilities out, pick a token, repeat. No learning happens. If output is bad you do not fix weights, you fix prompt, sampling, or model.

Related Wikipedia: Machine learning, Inference, Training.

Rust link: your engine will load weights once, then never change them during inference. That makes the code simpler.

2. How modern AI works, tiny version

Words you need: token - a small piece of text the model reads. tokenization - splitting text into tokens. embedding - turning a token into a list of numbers. transformer - the type of model most chat AIs use. autoregression - building output one piece at a time, each step looking at past steps.

Modern chat models are almost all decoder-only transformers [1][2]. That is a transformer that writes left to right.

Worked token example

Take "Hi there". A tokenizer might split this into ["Hi", " there"] which is 2 tokens. Each token gets an ID like [4438, 612]. Each ID looks up an embedding vector, for example 4096 numbers for a 7B class model. The stack of transformer layers then updates each vector by letting it attend to earlier vectors [1].

Sampling in plain words

After the last layer, the model outputs one score per vocab item, called logits. Logits turn into probabilities. Sampling is the rule that picks the next token from those probabilities:

  1. Tokenization splits "Hello world" into tokens like ["Hello", " world"]. Tokens are often words or word parts. See Tokenization.
  2. Each token becomes an embedding, a list of numbers like [0.2, -0.5, 0.9]. This gives the model math to work with.
  3. Attention - the part where each token looks at other tokens to get meaning. "Bank" looks at "river" to know it is not a money bank. See Attention and the Attention Is All You Need paper [1].
  4. Autoregression means predict one token, add it to the input, repeat. Like typing where each new word can see all past words.
  5. Sampling - picking the next token from probabilities. Greedy means pick the best one. Temperature rescales probabilities before picking: below 1.0 sharpens toward the top choice, above 1.0 flattens toward random. Top-k keeps only the k best tokens then samples. Top-p, also called nucleus sampling, keeps the smallest set whose probabilities add up to p, so the pool grows when the model is unsure and shrinks when it is sure [19]. See Language model.
flowchart LR A[Text: How are you?] --> B[Tokenization: How, are, you, ?] B --> C[Embeddings: lists of numbers] C --> D[Transformer layers + Attention] D --> E[Sampling: pick next token] E --> F[Repeat until stop]

3. The core loop

Words you need: prompt - input text from the user. prefill - first pass that reads the whole prompt. decode - loop that writes one token per step. detokenization - turning tokens back into text.

Every request follows the same loop:

  1. Turn prompt into tokens.
  2. Prefill once: read all prompt tokens in parallel, save notes.
  3. Decode many times: write one new token, add it to notes, repeat until stop word or max length.
  4. Detokenization: turn all output tokens back into text for the user.
flowchart TD P[Prompt tokens] --> PR[Prefill: 1 parallel pass] PR --> K[(KV cache: notes)] K --> D1[Decode step 1: write token A] D1 --> K K --> D2[Decode step 2: write token B] D2 --> K K --> D3[Decode ... until stop] D3 --> T[Detokenize to text]

If answer is 200 tokens long, that is 1 prefill plus 200 decode steps [3][4].

Worked loop with stop rules

Prompt "2+2=" becomes tokens [1, 19, 11, 19, 28]. Prefill reads all 5 at once. Decode step 1 might emit " 4". Decode step 2 might emit end of string. That stop token ends the loop. You also stop at max tokens, a safety cap like 256, so a bad loop cannot run forever.

Pseudo loop you will write in Rust:

tokens = tokenize(prompt)
cache = prefill(model, tokens)
for _ in 0..max_tokens {
  next = decode_one(model, tokens, cache)
  if next == EOS { break }
  tokens.push(next)
}
text = detokenize(tokens)

More: Modular LLM Inference Handbook, IBM What is LLM Inference.

Rust link: your main loop will be a while loop around decode. Get this loop right before any speed tricks.

4. Prefill vs decode

Words you need: compute bound - slow because math is heavy. memory bound - slow because moving data is heavy. TTFT and TPOT are defined in section 6.

Prefill reads the whole prompt at once. It does big matrix math in parallel. It is compute bound [5].

Decode writes one token at a time. Each step must load all weights plus all past notes. It is memory bound, limited by how fast data moves, not by math [3][5].

AspectPrefillDecode
WhenOnce per requestOnce per output token
Input sizeMany tokens at onceOne token
BottleneckCompute boundMemory bound
SetsTime to first tokenStreaming speed
Can it run with other requests?Yes, but heavyYes, good for batching

Because they stress hardware differently, some big systems run prefill and decode on different GPUs. That is called disaggregation [20][21].

Why split them

Colocated serving batches prefills and decodes together, which causes interference: a long prefill stalls streaming decodes. DistServe assigns prefills and decodes to different GPUs, removes that interference, and tunes each side separately for TTFT and TPOT [20]. The cost is moving KV cache over the network between the two sides, so placement follows cluster bandwidth [20][21]. Sarathi-Serve is the alternative when you stay colocated: split long prefills into chunks so decodes keep flowing [22].

More: AI21 Prefill and Decode, Sladyn Inference Notes.

5. KV cache, the bridge

Words you need: KV cache - saved keys and values so we do not recompute them. key and value - two number lists per token used by attention. query - number list for the current token that looks up keys.

During attention, each token makes a query, a key, and a value. Query asks "what do I need". Key labels "what I offer". Value holds the actual meaning.

Without cache, step 200 would recompute keys and values for all 199 past tokens. That is very wasteful.

The KV cache saves keys and values after prefill. Each decode step then only computes one new set and reuses the rest.

Size formula with worked numbers

Per token cache in bytes is:

2 x layers x KV_heads x head_dim x bytes_per_value [23][24]

The 2 counts keys plus values. Use KV heads, not query heads. Use 2 bytes for FP16 or BF16, 1 byte for FP8 [23][25]. Total is per token times tokens times concurrent requests [24].

Worked example from published configs: a 32 layer GQA model with 8 KV heads, head dim 128, FP16 gives 2 x 32 x 8 x 128 x 2 = 131,072 bytes, which is 128 KiB per token [24]. At 16,384 tokens and 8 concurrent requests that is 16 GiB. The same shape with 32 KV heads would be 512 KiB per token and 64 GiB total, which shows why head count matters [24]. Real tables show the same linear growth: for example Qwen3-8B is about 150 KB per token in FP16, so 1,000 tokens is about 0.15 GB and 100,000 tokens is about 14.75 GB for one request [26].

Fewer KV heads: MQA and GQA

Standard attention keeps one KV head per query head. Multi-query attention keeps many query heads but only one shared KV head, which cuts cache by roughly the head count [27][28]. Grouped-query attention keeps many query heads and shares a smaller set of KV heads across groups [29]. For example 32 query heads share 8 KV heads, so each KV head serves 4 queries and cache is about one quarter of full attention [30]. Queries stay distinct, so each head can still form its own weights [30]. This is why modern configs list both counts, like 32 query heads and 8 KV heads.

sequenceDiagram participant P as Prompt tokens participant M as Model participant C as KV cache P->>M: prefill all tokens M->>C: write keys + values loop each decode step M->>C: read all past keys + values M->>M: compute 1 new token M->>C: append 1 new key + value end

Problem: the cache grows with length and users. For long chats it can be larger than the model itself [6]. That is why sections 8 and 9 exist.

6. How we measure it

Words you need: TTFT - time to first token. TPOT - time per output token. throughput - tokens or requests per second. latency - total wait time.
MetricPlain meaningSet by
TTFTHow fast answer startsPrefill speed plus queue wait
TPOTHow fast it streams after startDecode speed
LatencyTotal time for one requestTTFT plus TPOT times token count
ThroughputHow many users you serveBatching plus memory tricks

Chat users feel TTFT and TPOT. Owners feel throughput and cost per token.

Worked latency math

Latency is about TTFT plus TPOT times output tokens [21]. Example: TTFT 0.4 seconds plus 100 tokens at 0.03 seconds each is 0.4 + 3.0 = 3.4 seconds. This is why long answers are ruled by decode speed even when prefill feels fast.

What good looks like depends on app, but the pattern from serving work is stable: chat wants low TTFT under about 1 second and smooth TPOT, code and agents tolerate higher TTFT but still need steady streaming, and offline batch jobs care about throughput, not TTFT [20][21]. Measure all three from day one: TTFT, TPOT, tokens per second.

7. Doing more at once: batching

Words you need: batch - group of requests run together. static batching - wait for whole group to finish. continuous batching - add and remove requests each step. chunked prefill - split long prompt into small pieces.

GPUs are very parallel. Running one request at a time wastes them.

Static batching waits for the slowest request. Continuous batching, also called iteration-level scheduling, lets a new request join at each decode step and lets finished ones leave early [10][16]. This keeps the GPU full.

Chunked prefill cuts a long prompt into chunks so one big prefill does not block everyone else's decode [22][31]. vLLM batches pending decodes first, then fills leftover token budget with prefill chunks. Smaller max_num_batched_tokens helps streaming, larger helps TTFT [31].

Orca in one paragraph

Static batching waits for the slowest request, so short jobs queue behind long ones. Orca proposed iteration-level scheduling: run one model iteration, return finished requests at once, admit new ones at once [32][33]. It adds selective batching because attention needs per request handling when lengths differ [32]. Reported result on GPT-3 175B was about 36.9x throughput at the same latency versus FasterTransformer in that setup [32]. Modern engines copy this idea under the name continuous batching.

8. Saving memory

Words you need: PagedAttention - store KV cache in small pages like OS memory. prefix caching - reuse KV cache for shared prompt start. eviction - delete less useful cache to save space.

8.1 PagedAttention

PagedAttention splits KV cache into fixed blocks or pages, with a table that maps where each request lives [9]. This avoids holes and waste. It was introduced by vLLM / PagedAttention paper.

8.2 Prefix caching

Many prompts share the same start, like system instructions or the same document. Prefix caching computes that shared start once and reuses it [6][17]. vLLM does this with hash based block reuse: it hashes token blocks plus parent hashes, so an exact shared prefix hits cache and skips recompute [34]. Changing one early word breaks the match, so keep shared text byte identical and put variable user text at the end when you can.

8.3 Other savers

  • KV quantization - store cache in fewer bits.
  • Eviction - drop old or low-score tokens, like StreamingLLM or H2O.
  • Offload - move cold cache to CPU RAM.

More: DeepLearning.AI vLLM lesson, Google Cloud Efficient Frontier.

Rust link: you do not need paging yet. Just log cache size in MB per request to feel the problem.

9. Going faster

Words you need: quantization - use smaller numbers to move less data. speculative decoding - guess several tokens fast then check with big model. FlashAttention - faster attention that avoids slow memory trips.
  • Quantization: FP16 to INT8 halves memory. INT4 quarters it. Since decode is memory bound, smaller weights stream faster. Methods like AWQ [13] and GPTQ [14] keep quality high. GPTQ is post training: each row is quantized to minimize error, weights stay INT4 on disk and are restored to FP16 on the fly in a fused kernel, which can save about 4x memory [35]. AWQ protects salient channels found from activation stats, stores packed 4-bit weights plus FP16 scales per group, and dequantizes on the fly for the matmul [36]. See Quantization.
  • FlashAttention / FlashInfer: fused kernels that keep attention math in fast on-chip memory. See FlashInfer paper [11][12]. FlashAttention is exact attention with IO aware tiling, not an approximation [11]. FlashInfer adds block sparse KV formats plus load balanced scheduling for serving [12].
  • Speculative decoding: small draft model guesses 3 to 5 tokens, big model checks them at once [16]. Lossless variants keep the target distribution identical while cutting latency [37]. Studies report the sweet spot is often 3 to 5 draft tokens with a draft model 10 to 20 times smaller, because bigger drafts cost too much to run and longer drafts get rejected too often [38]. vLLM exposes this as draft model, n-gram, EAGLE, and related methods with a settable speculative token count [39]. If correct, you saved steps. See Baseten Optimization Guide.
  • Disaggregation: run prefill GPUs and decode GPUs separately so neither waits.

Rust link: skip these at first. Your first speed win is just using f32 correctly and avoiding reallocation in the decode loop.

Request path in order

1. Router receives HTTP, picks a replica with free KV slots [17]. 2. Engine tokenizes and looks up prefix cache [34]. 3. Scheduler admits the request if KV budget allows, else queues or preempts [31]. 4. Model runner executes prefill or decode with fused kernels [7][15]. 5. Sampler picks the next token with your temperature and top-p [19]. 6. Stream the token and repeat. This is the same loop as vLLM Engine Core plus API server split, and the same split as TensorRT-LLM Scheduler plus KVCacheManager plus ModelEngine [7][15].

11. Your Rust map

Words you need: crate - a Rust package. module - a file or folder inside a crate that groups code.

Build in this order. Each maps to a wiki section above.

  1. tokenizer.rs - load a simple tokenizer, test encode and decode. Maps to section 2.
  2. model.rs - load tiny weights, run one matmul. Maps to section 2.
  3. attention.rs - single head attention with no cache. Maps to section 2.
  4. kvcache.rs - Vec based cache, then measure MB growth. Maps to section 5.
  5. decode.rs - greedy loop plus TTFT and TPOT timers. Maps to sections 3, 4, 6.
  6. batch.rs - from batch 1 to naive batch 4. Maps to section 7.
  7. server.rs - tiny HTTP streaming endpoint. Maps to section 10.
  8. Later: paging, quantization, speculation. Maps to sections 8 and 9.

Rule: do not add batching until single prompt streaming is correct. Do not add quantization until you can log cache size.

Tests that prove each step

Tokenizer round trip: decode(encode("hello world")) must equal input. Attention: single layer with no cache must match a naive math version to 1e-5. KV cache: decode with cache must equal decode without cache token for token. Metrics: log TTFT, TPOT, and cache bytes per request on every run, then use the formula in section 5 to predict if the next request fits [23][24].
